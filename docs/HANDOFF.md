### 数据留存清理（2026-08-18 做完）

`backend/src/handlers/cleanup.ts` + 每天 04:00 的定时触发器。**这不是可选的运维脚本**：
隐私政策第七节把保留期写成了具体天数，这个任务就是那段承诺的兑现物；
《个人信息保护法》第十七/十九条也要求告知保存期限并且不超过必要的最短时间。

| 数据 | 保留期 | 判定字段 |
|---|---|---|
| 登录日志 logins | 90 天 | `at` |
| 行为事件 events | 90 天 | `at` |
| 崩溃 crashes | 末次发生后 180 天 | `lastAt`（不是 firstAt——还在复发的 bug 不该被清） |
| 意见反馈 feedback | 处理完成后 1 年 | `handled==true && createdAt`，**未处理的永不清** |
| 注销用户 | 30 天后物理删除 | `users.deletedAt` |

- **改天数要同步改隐私政策第七节的表格**，两边必须一致，否则又变成说了没做
- 注销现在是「立即失效 + 30 天后物理删」：`softDeleteUser` 打标记时顺手盖
  `deletedAt`，清理任务据此判断到期。到期时 `hardDeleteUser` 会连带清掉该用户的
  wishes/tasks/letters/logins/events/feedback/deletion_requests，崩溃记录只清 account
  归属字段（那条指纹下还聚合着别人的崩溃次数，整条删会丢别人的数据）
- 每次运行每类最多 300 条、用户最多 20 个——云函数超时只有 20 秒，宁可分几天删完。
  实测跑一次 2.4 秒
- 🔴 **总开关默认关，目前是关着的**（2026-08-18 上线时先关掉观察）。
  管理端「公告与版本 → 功能开关 → 数据留存清理」可开。开关存在 `sys_features`
  文档的 `cleanupEnabled` 字段
  - **兜底方向跟 showRank 相反**：showRank 读不到配置按「开」，清理读不到按「关」。
    这是有意的——会物理删数据的自动任务，配置异常时宁可漏删不可错删
  - ⚠️ **长期关着 = 隐私政策第七节的承诺没兑现**，而且 logins/events 会一直涨到
    把管理端首页统计撑失真。观察一阵没问题就该打开
- 手动跑：`POST /admin/cleanup`（带 X-Admin-Key）；开关关着时手动也不跑，
  传 `{"force":true}` 可以强制跑一次（验证用）。定时器：
  `tcb fn trigger create api --trigger-name dailyCleanup --cron "0 0 4 * * * *"`
  ⚠️ 触发器配置在云端，不在仓库里（cloudbaserc.json 是 gitignored）——
  **换环境/重建函数后要记得重新创建这个触发器**，否则清理会静默停止
- 实测验证过完整链路：造账号→产生心愿和登录日志→注销→把 deletedAt 改到 31 天前→
  跑清理→用户记录和全部关联数据确认物理消失
- 首次运行给 78 个早期注销的测试账号补盖了 `deletedAt`（那个字段是这次才加的，
  老数据没有，不能当成"很久以前删的"直接清掉，所以补成当下重新计时）
- **顺带解决了一个性能隐患**：`allLogins`/`allEvents` 是拉全量没分页的，
  破千条后管理端首页统计会静默失真（见上面「计划 A 遗留事项」第一条）。
  90 天保留期把这两张表的规模钉住了

### 几个容易踩的点（都已踩过并修掉）

- **别把上传路径改成「按用途固定文件名然后覆盖」**。App 按去掉签名的稳定链接做磁盘缓存，
  覆盖同名文件的话 URL 不变 → 缓存永远命中旧图，用户得重装 App。现在 `admin/upload.ts`
  每次生成随机路径是**有意为之**，那里留了警告注释。
- **云存储链接直接 `Image.network` 取不到**（403），必须走 `/photo-urls` 换临时链接，
  统一用 `WishPhoto` 组件，它已经封装好了换链接 + 失败回退。
- **临时链接每次签名都不同**，所以缓存 key 必须用去掉 `?` 后的稳定链接，否则内存/磁盘
  缓存全都命中不了，表现就是每次进页面闪一下。
- **图片分配用 `doneNumberOf(w)` 轮流**，不是 id 哈希取模——哈希不保证均匀，实测 11 条
  分 4 张是 4/4/2/1，用户观感就是「没换」。
- `/config` 在**启动、登录、切回前台**（5 分钟节流）三个时机拉。运营改完图，用户切个
  后台再回来就生效。

   - **架构**：崩溃当下**只写本地不发网络**（进程可能马上没了、用户可能没网），下次启动补发，发成功才清。后端按指纹（异常类型 + 堆栈前几帧，剔除地址/数字）聚合，同一 bug 崩一万次归成一条只累加 count。
   - **三层覆盖**：① Dart 层未捕获异常（两端都有，完整可读堆栈）② 原生崩溃（**只有 iOS**，KSCrash 2.6.0）③ 异常退出计数（启动写 alive 标记、正常退后台清除，两端都有）。
   - ⚠️ **Android 的 xCrash 已摘除，别再加回来**：实测它的 `libxcrash.so` LOAD 段 `align=0x1000`（4KB），过不了 Google Play「targetSdk>=35 必须支持 16KB 内存页」的要求（2025-11-01 起，延期至 2026-05-31）——上架硬阻塞，16KB 页真机也加载不了。根因是它停更在 NDK r28 之前。**当时用 4KB 页模拟器测试全过，是模拟器骗人的典型案例**；这类 native 库合规问题必须直接查构建产物（`llvm-readelf -l xxx.so` 看 LOAD align）。
